2026-08-10 evidence review

QIE SafeRoute：不是明显复制，但必须加强产品楔子

结论

公开直接竞品：未发现。在检索到的 QIE 官方仓库和公开黑客松项目中，没有发现同时提供 QIE 0x/qie1 双向解析、受限 EIP-712 控制证明、离线 JSON/QR 验证的产品。但这不等于法律意义或全球范围的“绝对首创”；私有仓库、未索引项目和未公开提交无法排除。

建议：Pivot / 有条件继续。保留已经实现的安全内核，但不要只以“地址转换网页”参赛。应定位成可嵌入钱包、交易所充值页和商户结账页的 QIE Payment Intent Preflight SDK。

竞争矩阵

类别证据与 SafeRoute 的关系
QIE 直接竞品对公开 QIE 项目与 GitHub 关键词检索未发现相同组合；空仓库 q-chain-verify 不构成产品。公开空间稀疏，但搜索不可能证明绝对不存在。
QIE 邻近项目QIEPay、QIE MerchantPay、RemitChain、Leash、QIE Lens、TrustPass。它们做支付、汇款、代理钱包、浏览器或身份；不是双地址预检。支付项目可成为集成对象。
地址转换替代品Cosmos EVM Bech32 precompile、Injective SDK、Initia/XRP EVM 文档、Zilliqa 地址转换器。证明转换本身是成熟通用能力，不能作为主要创新点。
钱包控制证明替代品Mesh Verify、Iron、PayPal 自托管钱包签名说明、通用 SIWE/EIP-712。证明控制权有商业用途，但单独的消息签名也不是新技术。
非加密替代品交易所人工白名单、地址簿、测试小额转账、客服确认。慢、不可移植，但用户已经有工作流，SafeRoute 必须显著降低集成成本。

需求证据

  • QIE 官方文档确认“单一私钥、两种钱包格式”，0x 用于 EVM，QIE 原生格式用于原生功能。这证明技术前提真实。
  • Cosmos EVM 官方文档专门提供地址转换预编译，并警告派生配置错误会导致账户与余额难以关联。这证明双栈地址处理属于真实工程问题。
  • Evmos 与 Injective 的公开用户案例反复出现“外部钱包不接受地址”“0x 与 bech32 网络/格式混淆”等问题。这是跨生态的真实行为证据，但不能自动等同于 QIE 当前需求。
  • QIE 生态已有多个支付、汇款和钱包项目，说明存在潜在集成面；尚无证据表明这些团队愿意集成 SafeRoute。

需求评分：1.5/3（弱到中等）。有真实结构性问题和邻近用户，但缺少 QIE 团队访谈、集成承诺、使用数据或公开 issue。

当前版本的主要风险

  1. 转换逻辑可被几十行成熟库替代，独立网页容易被评为“太简单”。
  2. 控制证明目前证明地址控制，但没有绑定具体金额、代币、订单、请求方或付款上下文，实际支付价值不够强。
  3. 它不需要主网交易即可工作，与 Hackathon 3.0 的“Mainnet only / traction”叙事存在适配风险。
  4. 没有真实集成或用户反馈，不能声称已经实现产品市场验证。

推荐调整

升级为 QIE Payment Intent Preflight SDK：在现有地址对与签名基础上，将证明绑定到付款意图，包括收款账户、链 ID、金额、代币、订单号、请求方/audience、目的地址类型和过期时间；提供可嵌入组件与服务端验证器，并把 Demo 放进真实的商户结账或交易所充值流程。

最低验证门槛：联系 5 个 QIE 钱包/支付/交易所项目，获得至少 2 次具体问题访谈和 1 个愿意试集成的团队。达不到就停止继续扩建，只把当前成果作为开源工具提交。
